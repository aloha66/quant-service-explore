# K线图数据获取、入库与补偿策略（仅 K 线）

> 状态：PostgreSQL 下后续 K 线图数据获取、缓存、入库、补偿、查询与实时交易行情处理的约束基线；本文不提供 DDL、业务代码、数据库迁移、接口或定时任务实现。
>
> 范围：股票、指数、ETF 的 OHLCV K 线、Tick、实时行情，以及直接决定它们历史可解释性的证券、交易日历、股票池和板块成员 PIT（point-in-time）依赖。
>
> 排除项：财报、研报、公告、新闻、资金流、因子等不是本文的 K 线事实数据，不能写入本文定义的 K 线事实表；它们如被使用，只能以各自契约的外部依赖引用出现。

## 1. 决策摘要

采用 **QMT 本地历史缓存 + 应用临时缓存 + PostgreSQL 持久事实库** 三个独立生命周期，而非把“未写 PostgreSQL”误解为“不保存数据”。三者容量、下载范围、清理责任和可观测性彼此独立。

1. QMT 是长期 K 线事实的默认且唯一主来源。第三方（包括经 `a-stock-data` 调用的来源）仅能 `display_only` 或做显式质量比较；未经来源契约批准，绝不写入长期 K 线事实，也不按时间与 QMT 静默拼接。
2. 首期持久化全市场 QMT 前复权 `1d` 日线。分钟事实表只在第一个实际盘中策略池启用；Tick 不建设全市场事实仓。日、周、月与分钟策略是否长期入库，由数据集/策略登记的基础周期和保留期决定，不以“所有策略都存 1m”替代需求分析。
3. 长期基础 K 线事实固定为 QMT `dividend_type='front'`、`fill_data=False`。前复权的 QMT 返回值是默认研究/图表/趋势序列；必须保留该响应、采集时间和复权快照证据。除权或供应商修订须检查已封存历史，按完整系列快照切换，不能只追加新日期而混合不同复权基准。周/月等派生序列继承此前复权口径，不能再次复权或覆盖基础事实。
4. 日终异动、正式涨幅榜和可用于研究/回测的 K 线只读取 `quality_status=SEALED` 的 coverage，并固定其事实版本清单和系列快照。`DEGRADED` 只能返回带状态的数据预览或经调用方显式接受的降级读取，不能产生日终正式榜单或无标识地进入回测。是否被替代与质量状态分开记录。
5. 实时交易标的是小范围订阅。行情时间未知、断线或缺口超过阈值时进入 `STALE_DATA`，禁止新开仓；恢复订阅、补齐历史并验证后才可解除。

这是一项数据生命周期和可复现性决策，不是“所有数据入库”或“完全不保存”的二选一。

## 2. QMT 官方能力与采集边界

本节以迅投 QMT 官方文档为准。适配器必须在 `data_contract_version` 中固定 `api_family`（内置 `ContextInfo` 或原生 `xtquant.xtdata`）、完整调用入口、参数和返回形态，并记录实际 QMT 客户端、Python 包版本与权限。两个 API 家族不能仅凭同名函数互换；目标家族尚未选定或预检未通过时，只能采集受控样本。

### 2.1 历史、实时与本地缓存读取链路

QMT 历史的标准路径是：

```text
download_history_data
  -> QMT 客户端本地历史缓存
  -> get_market_data_ex / get_local_data
```

- `download_history_data` 下载指定标的、基础周期和时间范围至 QMT 客户端本地历史。内置 API 文档提示部分客户端不支持 `incrementally`；原生 `xtdata.download_history_data` 列出该参数，且说明同步完成后返回。支持情况、默认增量行为和完成判据必须按所选家族与版本预检；增量下载不等价于刷新此前已下载的修订历史。[内置行情函数](https://dict.thinktrader.net/innerApi/data_function.html)、[原生 XtData](https://dict.thinktrader.net/nativeApi/xtdata.html)
- 内置 `ContextInfo.get_local_data` 被官方标记为“不推荐”；原生 `xtdata.get_local_data` 是从本地文件批量读取历史的接口，列有 `fill_data` 和 `data_dir` 参数，不能套用内置 API 的弃用说明。本地数据不足时须先按下载策略补充；既有数据是否来自下载或订阅应记录证据。
- 内置 `ContextInfo.get_market_data_ex` 支持 `subscribe=False`，此时不订阅、只读本地已有数据；原生 `xtdata.get_market_data_ex` 没有该参数，最新行情需另行 `subscribe_quote`。历史与订阅实时同时存在时，`gmd` 系列可自动拼接。因此历史采集必须指定闭合的读取范围并校验完成边界，不能把“本次未调用订阅”当作“响应不含实时数据”的证明。[QMT：股票数据](https://dict.thinktrader.net/dictionary/stock.html)
- “本地读取为空”只证明此次读取没有返回数据，**不**证明停牌、无成交、未下载或上游无数据；原因必须结合下载记录、缓存范围与状态证据分类。

### 2.2 QMT 基础周期与允许的派生周期

QMT 历史实际存储的基础周期为 `tick`、`1m`、`5m`、`1d`。历史读取合成周期前，必须先下载其基础周期：

| 目标周期 | 历史基础周期 | 规则 |
| --- | --- | --- |
| `tick` | `tick` | 原始 Tick；不作为全市场长期事实集。 |
| `1m` | `1m` | 仅在策略确实需要 1 分钟特征时选为持久基础周期。 |
| `3m` | `1m` | 由 `1m` 合成。 |
| `5m` | `5m` | 可作为仅需 5m 及其派生周期的持久基础周期。 |
| `10m`、`15m`、`30m`、`60m`（及官方列出的更长分钟/小时周期） | `5m` | 由 `5m` 合成；不得假定可由 `1m` 或第三方数据替代。 |
| `1d` | `1d` | 全市场日线的首期基础事实。 |
| `2d`、`3d`、`5d`、`1w`、`1mon`（及更长日历周期） | `1d` | 由 `1d` 合成。 |

实时订阅可直接订阅合成周期；这不改变历史入库只能以其官方基础周期下载和校验的规则。官方将 `1w`、`1mon` 作为周期名称；本文的业务标签“周/月”分别对应它们，不使用未定义的 `1mo`。

### 2.3 QMT K 线与 Tick 字段映射

下表是长期基础 K 线事实的逐项字段契约。不同 API 家族的字段名和枚举有差异；适配器须按完整入口和实际响应固定映射，保留原始键名与值。字段缺失与字段存在但为空必须分开记录；品类不适用的空值可以保留，必需字段缺失或无法识别的返回形态必须阻止事实晋升。

| QMT 字段 | 事实字段 | 官方含义 | 入库规则 |
| --- | --- | --- | --- |
| `time` | `source_bar_time` | 时间 | 未经边界样本验证前，禁止改名为 `open_time` 或推定它是 bar 起点。保存原值、解析规则和 QMT 客户端版本。 |
| `open` | `open` | 开盘价 | 保存 QMT `dividend_type='front'` 返回的数值；不在应用侧二次复权。 |
| `high` | `high` | 最高价 | 原样数值，校验非空时 `high >= max(open, close, low)`。 |
| `low` | `low` | 最低价 | 原样数值，校验非空时 `low <= min(open, close, high)`。 |
| `close` | `close` | 收盘价 | 原样数值；未完成实时 bar 不能成为正式事实。 |
| `volume` | `volume` | 成交量 | 原样值及单位随 `data_contract_version` 固化，不在查询时猜测股/手。 |
| `amount` | `amount` | 成交额 | 原样值及币种/单位随契约固化。 |
| 内置字段说明为 `settle`；原生 K 线字段表为 `settelementPrice` | `settle` | 今结算 | 按 API 家族、版本及样本固定别名映射，不擅自修正上游拼写；若响应含多个候选键且值冲突，保留证据并阻止晋升。证券品类不适用时允许空/官方返回值。 |
| `openInterest` | `open_interest` | 持仓量 | 保留；不以股票常见的无意义值替代。 |
| `preClose` | `pre_close` | 前收盘价 | 保存 QMT 前复权响应中的字段；派生周期必须另定其选择规则。 |
| `suspendFlag` | `suspend_flag` | 内置字段说明列 `1` 停牌、`0` 不停牌；原生字段表另列 `-1` 当日起复牌 | 保留原值；`1` 是 `SUSPENDED` 的可认可证据之一，`-1` 不得映射为停牌。枚举按家族/版本验收，未知值不得静默归为正常。 |

上述差异以[内置行情函数字段](https://dict.thinktrader.net/innerApi/data_function.html)和[原生 XtData 字段表](https://dict.thinktrader.net/nativeApi/xtdata.html)为核验入口；文档与实际返回有差异时，先记录样本并修订映射契约，不静默丢列。Tick 与 K 线是不同事实形态，不把 Tick 的累计量或盘口字段塞进 K 线行。至少映射：

| QMT Tick 字段 | Tick 事实/快照字段 | 官方含义与处理 |
| --- | --- | --- |
| `time`（可同时保存 `stime`） | `source_tick_time`、`source_tick_time_text` | 时间戳及其字符串表现；保持原值和解析规则。 |
| `lastPrice` | `last_price` | 最新价。 |
| `lastClose` | `last_close` | 前收盘价。 |
| `open`、`high`、`low` | `session_open`、`session_high`、`session_low` | 当日开/高/低；不是 Tick K 线字段。 |
| `volume`、`amount` | `cumulative_volume`、`cumulative_amount` | 官方为累计成交量/成交额语义；单位随契约固化。 |
| `stockStatus` | `stock_status` | 证券状态；不能自动等价为 K 线的 `suspendFlag`。 |
| `askPrice`、`askVol` | `ask_prices`、`ask_volumes` | 多档委卖价/量，保留原始列表与长度。 |
| `bidPrice`、`bidVol` | `bid_prices`、`bid_volumes` | 多档委买价/量，保留原始列表与长度。 |

不得把文档示例中的五档列表泛化为所有订阅、证券或权限的固定盘口深度；实际字段可用性、列表长度和 Level2 权限由 QMT 能力预检及原始响应决定。QMT 官方说明 Tick 周期均为不复权，因此 Tick/实时交易快照保留实际收到的实时价格，不能与前复权 K 线数值混作同一价格序列。[QMT：股票数据字段](https://dict.thinktrader.net/dictionary/stock.html)

### 2.4 时间、填充和基础事实口径

1. 长期基础 K 线读取固定 `dividend_type='front'`。保存 QMT 返回字段、`data_contract_version`、`adjustment_snapshot_id`、`ingestion_run_id`、接收时间和可读取原始响应证据。复权基准、因子使用范围和成交量/成交额是否变换必须通过所选 API 的样本验证并记录；不得凭参数名推定，也不得用应用侧二次复权替代 QMT 响应。调用方不得传入不同复权类型。
2. `dividend_type='none'`、`back`、`front_ratio`、`back_ratio` 均不是默认长期事实。既有或临时取得的这类序列必须以不同 `data_contract_version` 和 `source_selection_policy_id` 隔离；不得通过应用侧比例换算或按时间拼接并入默认前复权序列。
3. 所有用于正式基础事实、支持 `fill_data` 的读取入口均显式传 `False`，包括原生 `xtdata.get_local_data`；不允许调用方自行决定。理由是补值 bar 会掩盖“未下载/本地范围缺失/上游失败/停牌/无成交”的差异，进而错误封存 coverage。若某个入口不能关闭填充，且不能证明响应未填充，则该入口只允许受控样本或展示，不能晋升正式事实。
4. `fill_data=False` 不表示每个交易时段都必须有可成交 bar：停牌、无成交和真正缺失仍须依据 `suspendFlag` 或认可状态源、交易日历、原始读取结果和 coverage 规则分别判断。
5. 上线前必须取同一标的的 `09:30`、午休前后、`15:00` 边界样本，跨 `1m`、`5m`、`1d` 比对 `time`、字符串索引和实际成交区间，写入 `data_contract_version` 的时间标签结论。结论未通过前，唯一允许名称是 `source_bar_time`；派生 `bar_start_at` / `bar_end_at` 也不得用于正式聚合或分区键。此时只能保存受控样本，不能晋升为正式事实或创建 `SEALED` coverage。
6. coverage 中的 `trade_date` 是 PIT 交易日历给出的**目标交易日**，不是对 QMT `time` 的重命名；日线事实的分区交易日只能在上述 `1d` 时间标签验证通过后从已记录的映射规则得到。

### 2.5 基础行情完成与日终封存

时间标签验证只确定 bar 对应哪个区间，不能证明上游已完成当日行情。基础数据契约必须另行固定交易所时区、品类适用交易时段、收盘集合竞价、盘后交易的纳入范围、上游完成证据、收盘后等待及复核间隔。

- 全日日线默认覆盖该品类全部适用交易时段。QMT 官方提示普通股票收盘行情可能晚于 `15:00` 下发；创业板、科创板如需盘后定价交易数据，应在 `15:30` 收盘后获取。这些时间说明不是固定秒数的完成保证，须验证目标客户端的日线 OHLCV/amount 实际包含范围。[QMT：数据更新时间](https://dict.thinktrader.net/dictionary/question_answer.html)
- 正式封存须同时满足：所有纳入时段已结束，收盘后下载/读取成功，上游完成证据或已验收的延迟与重复读取稳定性规则通过，第 5.1 节全部预期单元闭合。仅到达 `15:00`、存在一行日线、价格不再变化或某次下载返回成功均不足以单独封存。
- 若客户端不能提供已完成标记，契约必须用边界样本确定最早读取时点、两次完整读取的最小间隔及 OHLCV/amount 一致性检查；不能设零间隔或仅比较收盘价。到重试截止仍未通过时为 `DEGRADED`。
- 盘后数据是否已包含无法验证时，不得把结果当作完整全日日线；若业务批准排除盘后交易，应登记独立时段口径，并仅在返回范围可验证时启用，不能与全日事实混用。分钟基础 bar 同样须通过其所在时间槽的结束与到达延迟检查。
- 封存后仍应按契约进行延后复核；供应商迟到成交或修订造成差异时，进入第 4.4 节修订流程，不覆盖旧事实和旧 coverage。

## 3. 三层数据生命周期与读取决策

### 3.1 三个独立存储域

| 生命周期 | 存什么 | 下载/写入范围 | 容量与清理责任 | 必须观测 |
| --- | --- | --- | --- | --- |
| QMT 本地历史缓存 | 下载产生的本地历史，以及经所选 API 验证会落地的订阅数据 | 只下载/订阅获批准的标的、基础周期和时间范围；合成历史先下载基础周期 | QMT 客户端/运行环境负责磁盘配额、目录和清理；应用 TTL 清理对此无效 | 记录下载/订阅入口、标的、基础周期、请求范围、客户端版本、完成/失败、缓存目录、磁盘占用、容量上限与剩余空间。 |
| 应用临时缓存 | `display_only` 响应、短时分钟图、未晋升的第三方展示数据 | 仅响应所需区间；与来源和到期时间绑定 | 应用负责 TTL、容量上限、驱逐和故障后可丢失；可以是不持久响应或 `UNLOGGED`/磁盘缓存 | 命中率、总大小、过期清理积压、来源、下载触发次数、TTL 和驱逐原因。 |
| PostgreSQL 持久事实 | 经来源契约、完整性校验和晋升规则批准的基础 K 线、coverage、任务、缺口和交易证据 | 只写批准的数据集和基础周期；第三方未获批准不得进入 | 数据平台负责分区保留、归档、备份与删除前检查 | 行数/分区大小、写入吞吐、覆盖率、缺口、revision、查询延迟、备份恢复。 |

`display_only` 的默认安全策略是：**QMT 本地没有所需历史时不自动下载**，返回 `HISTORY_NOT_CACHED`（或等价机器状态），并明确该状态不是停牌。产品若需要“展示请求可下载”，必须通过显式 `display_download_policy_id` 开启，限定可下载标的、基础周期、时间范围、QMT 磁盘预算和并发，并记录为 QMT 本地缓存下载；结果仅进响应/TTL 缓存，绝不触发 coverage 封存、异动检测、涨幅榜、回测或分钟事实晋升。该策略使系统可以触发 QMT 下载，同时避免一次性图表请求无界占用客户端磁盘。

### 3.2 读取与写入决策路径

```text
收到请求或采集意图
  |
  +-- 实时交易/风控证据？ -> 小范围 QMT 订阅 -> 实时流健康检查
  |                              -> 触发订单、撤单或风控拒绝：持久交易快照
  |
  +-- 已批准的长期数据集？ -> 按其 canonical_base_interval 检查 PostgreSQL
  |       |                         -> 缺口：创建/领取补偿任务 -> QMT 本地读取
  |       |                              （所需基础周期未下载时，依下载策略触发下载）
  |       |                              -> 校验 -> coverage 输入清单 -> 系列快照原子切换
  |       +-- 命中：固定 source_selection_policy_id + series_snapshot_id 后查询
  |
  +-- display_only？ -> 应用 TTL 命中：返回（带来源）
                         -> QMT 本地命中：读取后仅写 TTL/响应
                         -> QMT 本地未命中：默认 HISTORY_NOT_CACHED
                         -> 有显式 display_download_policy：下载基础周期后读取，仅写 TTL/响应
                         -> 仅 QMT 不可用时可读第三方展示，始终带第三方来源且不晋升
```

执行优先级固定为：**实时交易 > 当日封存 > 补偿/修订 > display_only**。优先级只约束资源领取和限流，不等同于本文实现任何调度器。

### 3.3 基础周期、策略登记与晋升

每一个长期数据集或策略必须在登记中声明：

- 稳定的 `dataset_id`、标的范围及绑定的 `source_selection_policy_id`；
- `canonical_base_interval`；
- 指标的“周期 + bar 数”，例如 `MA20@1d` 与 `MA20@5m` 是不同指标；
- 最早回放日期；
- 实时运行缓冲保留期；
- 归档/训练保留期；
- 删除前必须满足的引用、归档和复现校验条件。

选择规则如下：

| 需求 | `canonical_base_interval` | 长期写入规则 |
| --- | --- | --- |
| 需要 `1m` 特征 | `1m` | 仅该策略池的完整 `1m` 基础 bar 可晋升。 |
| 只需要 `5m`、`15m`、`30m`、`60m` | `5m` | 保存 `5m`；高阶分钟由它派生。 |
| 日、周、月趋势 | `1d` | 保存日线；周/月从受 coverage 约束的日线派生。 |
| 单次展示 | 无 | 可按 QMT 能力请求所需周期，但只写响应或 TTL 缓存。 |

“最近 3 个完整月”只可作为实时运行缓冲的初始默认值，绝不是回测、训练或长期复盘保留期。后者由登记的最早回放日期和归档保留期决定。

### 3.4 派生周期契约

每个派生周期必须绑定不可变的 `derivation_contract_version`，至少规定：交易所时区、交易日历版本、交易时段模板、午休与集合竞价是否纳入、时间标签（起点/终点）、OHLCVA 聚合、`preClose`、停牌状态、继承的 QMT 前复权口径、缺失基础 bar 和不完整桶的处理。

- `open` 为桶内首个有效基础 bar 的 `open`，`high` / `low` 为极值，`close` 为末个有效基础 bar 的 `close`，`volume` / `amount` 为求和；没有可接受的基础 bar 时不得伪造 OHLCVA。经第 5.1 节认可的 `SUSPENDED`/`NO_TRADE` 是已解释的空槽，不参与数值聚合；整桶为空时只返回状态，不能计为指标所需的有效 bar。
- `preClose` 不做“上一根恰好可见 bar”猜测；其来源/计算必须由契约规定。派生值继承基础 `front` 值，不得应用第二次复权。`suspend_flag` 只能来自被认可的基础状态证据或派生规则，不得由零量或空行推断。
- 预期时间槽缺少基础 bar 且无认可的空槽证据、午休边界不符合模板、或当前日/周/月尚未结束，均使派生条目 `completeness != COMPLETE` 或 `is_final=false`。
- 正式周/月只有在所绑定系列快照内**每个预期交易日**均满足 coverage 契约时才可 `is_final=true`。任何日为 `DEGRADED`、缺失、来源/契约不兼容或同一标的复权快照不一致时，禁止将剩余日线聚成正式周/月；至多返回附 coverage 状态的预览。派生结果固定输入清单，基础事实修订后生成新结果版本，旧结果保留其原输入。

## 4. 来源、事实和外部依赖契约

### 4.1 来源身份与物理共表边界

可在一个规范化事实表中物理共表，但逻辑系列必须隔离。每根长期事实至少携带：

- `upstream_source_id`：真实行情上游，如 `qmt`、`mootdx`、`tencent`；
- `adapter_id`、`adapter_version`：例如 QMT 适配器或 `a-stock-data` 适配器；
- `data_contract_version`：API 家族与调用入口、字段映射、单位、时间边界、时段与完成规则、固定的 `dividend_type='front'`、`fill_data`、校验和原始证据保留规则；
- `source_selection_policy_id`：不可变的查询选择策略；默认策略固定选择 QMT 的前复权 K 线；
- `ingestion_run_id`、接收时间、原始响应证据/不可变对象引用和完整性 hash；
- `source_bar_time`、基础周期、QMT 返回的价格字段、`bar_revision` 和 `adjustment_snapshot_id`；当前性从查询绑定的系列快照推导，不用一个全局行标志替代。

`a-stock-data` 是适配工具，绝不是单一 `source_id`；使用它时仍须记录其实际 `upstream_source_id`。hash 只校验内容完整性，不能成为唯一证据：原始响应必须可读取，或有受保留策略保护的不可变对象引用。对象删除前必须确认其所支撑的事实、coverage 与交易快照已无保留义务或已归档。

业务查询必须指定或继承 `source_selection_policy_id`。未获批的第三方数据可以进入临时缓存，但不属于任何长期选择策略、coverage、异动或回测数据集。跨来源比较只能输出显式质量报告（比较的来源、字段、差异与时间范围），禁止自动形成一条混源 K 线序列。

### 4.2 逻辑表与阶段边界（非 DDL）

| 阶段 | 逻辑对象 | 逻辑键、唯一性与保留/清理责任 |
| --- | --- | --- |
| 首期必需 | `kline_bar_1d` | QMT 前复权 `1d` 基础事实。唯一候选键含 `instrument_id + source_bar_time + canonical_base_interval + upstream_source_id + data_contract_version + bar_revision`；每行绑定复权快照，版本不可覆盖，查询经 coverage 输入清单选择精确版本。仅在 `1d` 时间标签验证通过后按映射出的交易日年分区，长期保存；数据平台在引用/归档检查后才能删除分区。 |
| 首期必需 | `kline_ingestion_run` | 一次下载/读取/校验批次，含范围、QMT 客户端版本、本地缓存观测、原始证据引用、计数、状态和错误摘要。不可覆写审计字段，长期保存。 |
| 首期必需 | `kline_sync_task` | 任务唯一键见第 5 节；持有租约所有者、截止时间、单调递增的 fencing token、优先级与重试信息。完成/取消记录按审计保留策略清理，不能早于关联 `run`。 |
| 首期必需 | `kline_coverage` | `trade_date + canonical_base_interval + universe_snapshot_id + upstream_source_id + data_contract_version + coverage_revision` 唯一；保存预期/实际/例外计数、`quality_status`、完成证据和 `coverage_manifest_id`。终态质量及输入清单不可覆盖；替代关系单独记录。长期保存。 |
| 首期必需 | 复权快照与输入清单 | `adjustment_snapshot_id` 固定第 4.4 节的复权证据；`coverage_manifest_id` 固定某个完整 coverage 键对应的精确事实版本和例外证据；`series_snapshot_id` 固定数据集跨日期使用的 coverage 清单。可保存为受保护的不可变对象或数据库清单，未变化部分可复用已有引用，不要求创建逐槽审计表。保留期覆盖全部引用者。 |
| 首期必需 | 当前快照指针与发布记录 | 以数据集和 source policy 为作用域，唯一选择当前 `series_snapshot_id`；指针更新及具有唯一事件 ID 的待发布记录与发布事务一起提交。第 5.2 节规定失败重放、去重及旧版本隔离。 |
| 首期必需 | `kline_gap` | `coverage` revision 下的标的/区间/缺失分类/尝试序号唯一；成功补洞也保留闭合记录。 |
| 首期必需 | `kline_cache` | 只存临时展示：键含标的、请求周期、区间、真实来源、契约、`expires_at`；按到期时间索引。可用 `UNLOGGED`，由应用 TTL 清理，永不成为事实输入。 |
| 首期必需 | `kline_source_contract`、`source_selection_policy` | 不可变版本及批准范围；禁止更新既有语义，只能新增版本/策略。长期保存。 |
| 首期必需 | 外部依赖引用 | 证券、交易日历、股票池快照、板块成员/分类快照的不可变 ID、版本、有效时间、来源与可读证据引用。它们不是 K 线事实表，也不把财报/新闻等写入 K 线域。 |
| 仅逐标的全量封存审计 | `kline_coverage_item` | 启用前先给出“标的数 x 交易日 x revision”（分钟扩展还须乘以预期槽数）的容量预算；按交易日月分区，保留期、冷归档位置和 revision 访问方式必须获批。未启用时，从必需的输入清单推导正常 `BAR_PRESENT`，只额外持久化 `SUSPENDED`、`NO_TRADE`、失败及范围缺失等例外；不得因此省略版本绑定。 |
| 第一个盘中策略池 | `kline_bar_minute` | 仅登记的数据集，逻辑键与日线一致但 `canonical_base_interval` 为 `1m` 或 `5m`；按 `source_bar_time` 月分区。按各策略登记的运行/归档保留期清理。 |
| 实际交易/风控链路 | `trade_market_snapshot` | 以交易决策/订单事件 ID 唯一；长期保存真实可读取的行情窗口与决策证据，不是全市场 Tick 表。 |

分区删除不是单纯 TTL：持久事实或审计分区在删除前必须通过依赖引用、当前 coverage、榜单/回测可复现性、对象证据归档和备份恢复检查。`UNLOGGED` 缓存可因故障丢失，不得与 QMT 客户端磁盘缓存混为一谈。

### 4.3 契约升级与历史系列

字段、单位、时间边界、复权方式、填充或校验规则的语义变化必须新建 `data_contract_version`，不得就地重写历史。`none -> front` 是不兼容变化：默认长期 policy 改为前复权后，旧不复权事实继续隔离，只能以显式历史 policy 查询，不能成为默认图表/研究/榜单输入。

按生效日期维护的 **series policy/version set 是版本路由表，不是允许拼接不同语义数据的规则**。新版本只对登记的生效范围生效；历史复现显式固定原 policy 与 `series_snapshot_id`。连续图表、指标和回测请求必须在同一可兼容系列中取得完整区间及预热窗口：

- 默认连续查询跨越不兼容契约时返回 `INCOMPATIBLE_SERIES_VERSION`，附边界和各段版本；默认 policy 的历史区间尚未重建时返回 `COVERAGE_UNAVAILABLE`，不能自动回退到旧不复权段，也不能悄悄缩短 MA20 等计算窗口。
- 调用方显式请求历史分段预览时，可分别返回各段及其 policy/contract，但标记 `continuous=false`；前端不连接跨段曲线，研究/回测不跨段聚合。兼容升级只有在不可变版本路由中记录已验收的兼容关系、证明单位/时间/填充语义一致且复权快照可复用后才允许连续读取；`none -> front` 不属于兼容关系。
- 只有明确批准“从 QMT 以 `front` 全量回读、完整校验、新 coverage 全部封存后切换”的迁移，才能把全历史选择策略切到前复权。单纯升级版本不自动触发全历史重算；第 4.4 节针对同一契约下真实除权或数据修订的必要刷新另行执行。

### 4.4 前复权快照与已封存历史修订

`data_contract_version` 固定处理语义，不能代替某次复权数据的版本。QMT 官方复权示例会将后续除权事件作用到此前价格，因此相同 `front` 参数与契约下，不同采集时点的历史返回仍可能不同。保留响应只能证明“当时取得什么”，不能自动保证多个采集批次处于同一复权基准。[QMT：复权计算方式](https://dict.thinktrader.net/nativeApi/code_examples.html)

1. 每个标的的 `adjustment_snapshot_id` 固定来源、契约、采集/核验时间、已验证的复权基准与作用范围、QMT 除权数据快照或经验证的等效版本证据，以及可读对象引用和 hash。因子快照用于识别变化与解释响应，不用于应用侧二次复权。相同证据可复用 ID，不能仅按采集日期或 `front` 字符串判定相同基准；无法验证时不能晋升。
2. 日终采集和停机恢复须检查除权证据变化；收盘后复核、供应商修订通知及登记的历史抽查也可触发修订。检查频率、最大未核验时长和回读预算由数据集登记；超过最大未核验时长仍无法完成检查时，按待修订处理并注明原因为核验不可用，不能宣称当前快照已验证为最新。修订不能仅依赖“未封存日期”扫描：即使全部日期已 `SEALED`，仍须检查已持久化系列。
3. 先登记本次修订原因与受影响标的、基础周期、日期范围和依赖者。除权基准变化须覆盖该标的仍供连续查询及指标预热使用的全部受影响历史；无法可靠界定时，按登记的完整保留区间回读。所有正在使用的基础周期分别验收。必须从 QMT 刷新/重读，不能只向本地缓存末尾追加，不能用应用比例换算；读取前后核验复权证据一致，期间变化则废弃候选并重新采集。
4. 重读生成新的 bar 版本、coverage revision 和不可变系列快照。同一标的参与一次连续计算的全部 bar 必须属于同一已验证复权快照；不同标的可有不同快照。新 `series_snapshot_id` 明确引用每个日期的完整 coverage 键及输入清单，未受影响的输入可以复用。范围内需要替换的 coverage 全部 `SEALED` 后，才按第 5.2 节原子切换当前系列快照。
5. 修订进行中或失败时保留旧快照，返回其原 `as_of` 和 `REVISION_PENDING`；要求最新一致序列的请求返回 `DATA_REVISION_PENDING`。新取得数据仅可作候选或带状态预览，不能与旧快照拼接。旧快照按原输入继续可复现；周/月、指标和榜单的最新结果须随新输入生成新版本。
6. 单次请求或研究任务开始时固定 `series_snapshot_id`，分页、跨日期和预热读取共用该快照，不能每次查询分别取最新 revision。历史结果复现固定原快照；声称模拟“当时已知信息”的回测还须限定证据可用时间，不能把今天回读的修订历史标成当时可见的数据。

## 5. 补偿、coverage 与并发状态机

四个实体分别表达不同状态，禁止混用。

| 实体 | 负责的问题 | 状态 |
| --- | --- | --- |
| `kline_sync_task` | 某个可领取工作是否可执行 | `QUEUED -> LEASED -> RUNNING -> SUCCEEDED`；失败可转 `RETRY_WAIT` 后重回 `QUEUED`，或转 `FAILED`/`CANCELLED`。依赖/权限/容量未满足时为 `BLOCKED`。`BLOCKED` 只属于任务。 |
| `kline_ingestion_run` | 一次实际下载、读取、标准化和校验批次 | `STARTED -> READING -> VALIDATING -> COMMITTED`，或 `FAILED` / `ABANDONED`。一个任务可有多个 run。 |
| `kline_coverage` | 一个交易日、范围和契约版本是否足以供正式消费 | `quality_status` 为 `PENDING -> BUILDING -> SEALED`，或 `PENDING/BUILDING -> DEGRADED`。终态质量和输入不变；`SUPERSEDED` 仅表示指定发布作用域内的替代关系，不是质量状态。不存在 `BLOCKED` coverage。 |
| `kline_gap` | 一个明确缺口及其处理结果 | `OPEN -> RETRYING -> RESOLVED`，或 `EXHAUSTED` / `WAIVED`；`WAIVED` 必须有批准理由，仅表示停止重试，仍是未满足的预期单元，不能成为 `BAR_PRESENT` 或使 coverage 封存。 |

```text
任务：       QUEUED -> LEASED -> RUNNING -> SUCCEEDED
                         |         |-> RETRY_WAIT -> QUEUED
                         |         |-> FAILED / CANCELLED
                         +-> BLOCKED --(依赖恢复后)--> QUEUED

批次：       STARTED -> READING -> VALIDATING -> COMMITTED
                                   \-> FAILED / ABANDONED

coverage 质量： PENDING -> BUILDING -> SEALED
                       \-> DEGRADED
系列选择：     snapshot N --(原子切换指针)--> snapshot N+1
旧 coverage：  原 SEALED/DEGRADED 保留，替代关系记为 SUPERSEDED
```

### 5.1 coverage、缺口与当前查询

覆盖范围由 PIT 交易日历、`universe_snapshot_id`、证券上市/退市状态、基础周期、来源、契约和交易时段共同定义，不能用“最新一条 bar”冒充完整水位。所有计数针对互斥的预期单元；修订股票池或时段须生成新的范围证据，不能在失败后缩减分母以制造完整率。

| 预期单元 | `BAR_PRESENT` 准入条件 | 认可的无 bar 情况 |
| --- | --- | --- |
| 日线：标的 x 目标交易日 | 输入清单中恰有一根通过字段、来源、契约、复权快照及第 2.5 节完成检查的日线版本 | 覆盖整个预期交易日的 `SUSPENDED` 或 `NO_TRADE` 证据；局部停牌不能豁免其他时段。 |
| 分钟：标的 x 交易日 x 预期时间槽 | 按已验证时段模板生成 `1m`/`5m` 槽位，每槽恰有一根时间边界、来源、契约、复权快照、数值和完成性均通过的 bar 版本 | 精确覆盖该槽的 `SUSPENDED` 或 `NO_TRADE` 证据；不得仅因当日日线存在就视为分钟完整。 |

- 午休及不在登记口径内的时段不生成预期槽。重复时间戳、错位或跨越时段边界的 bar 不满足槽位；零成交量或 OHLC 为空也不自动成为有效 bar。必需价格/量额字段的可用性按品类契约校验。已认定整槽停牌的响应保留为例外证据，不再计入 `BAR_PRESENT` 或参与数值聚合，避免重复计数。
- 正常数据统一命名为 `BAR_PRESENT`；确认应有但尚无可接受 bar 的缺口命名为 `MISSING_BAR`。其他缺口原因至少包括 `NOT_DOWNLOADED`、`LOCAL_RANGE_MISSING`、`DOWNLOAD_ERROR`、`UPSTREAM_ERROR`、`INVALID_BAR`。原因无法区分时记录 `UNKNOWN_MISSING` 及现有证据，不能猜测；`SUSPENDED`/`NO_TRADE` 是有证据的覆盖例外，不与抓取错误混称。
- 只有 `suspendFlag=1` 或契约认可且覆盖目标区间的证券状态证据，才能认可 `SUSPENDED`。`NO_TRADE` 必须有契约认可的完整区间证据，例如已验证覆盖整个槽位的交易记录或状态源；空响应、零量、超时、未下载或下载成功本身均不是充分证据。尚无可靠证据源的无 bar 单元保持缺口，不能伪造价格。
- `SEALED` 要求 `expected_count = bar_present_count + suspended_count + no_trade_count`，且每个预期单元只计一次、未解决/耗尽/豁免缺口数为零，并通过第 2.5 节完成检查。合法空槽允许 coverage 封存，但不产生可成交 bar。`WAIVED` 只能停止重试，coverage 仍为 `DEGRADED`；有效范围为空时记录其范围证据，不能伪造任何行情。
- 每个 coverage 终态必须绑定不可变的 `coverage_manifest_id`，列明每个正常单元的完整事实键和 `bar_revision`、复权快照，以及所有例外的区间、分类和证据。必须固定交易日历/时段/股票池版本与计数。可采用可读的分片或压缩清单，不能只存总数或 hash；未启用 `coverage_item` 时也必须能从清单唯一重建输入，禁止按每根 bar 的“当前/最大 revision”回查历史。
- 对 `DEGRADED` 补洞或对 `SEALED` 修订均创建下一 `coverage_revision`，重新计算完整范围和终态，不能只保存本次新增的 bar。原质量和清单保持不变；重试处理结果可以追加，但不得反向改变旧 coverage 的计数、例外或质量结论。旧版本是否被替代从指定数据集/source policy 的系列选择关系得出。
- 当前查询先固定当前 `series_snapshot_id`，再读取其中明确绑定的 coverage。`SEALED` 返回正式事实；`DEGRADED` 只返回带状态、缺口与版本的可用预览，正式榜单/默认回测不可使用。若新修订未就绪，按第 4.4 节返回旧快照及待修订状态；没有适用快照时返回 `COVERAGE_UNAVAILABLE`，不得把其他日期当作目标日数据。后台任务 `BLOCKED` 不改变既有 coverage 的质量，也不能使未完成候选成为当前。

### 5.2 幂等、租约与事务边界

`kline_sync_task` 的任务唯一键为：

```text
task_kind + upstream_source_id + canonical_base_interval + trade_date
+ universe_snapshot_id + data_contract_version + coverage_revision
```

上述键适用于按交易日工作的采集/修订任务。多日修订的最终发布任务使用 `publish_series + dataset_id + source_selection_policy_id + series_snapshot_id` 唯一键，关联全部候选 coverage；它只发布已完成的输入，不再次下载行情，同样遵守租约与 fencing 校验。

同一补洞/修订意图须在创建任务时原子分配或复用其目标 `coverage_revision`；终态前的重复投递和租约接管复用该版本，不能为每次重试分配新 revision 来绕过唯一键。已提交终态的任务重复投递只确认已有结果；终态后的新一轮补洞、数据修订或范围变化则建立新意图及版本。

worker 以带过期时间的租约领取任务（例如行锁/`SKIP LOCKED`）；领取时保存所有者、数据库时钟确定的截止时间及单调递增的 `fencing_token`。续租须匹配当前所有者/token；到期或释放后才可接管，接管增加 token。run、coverage 终态提交及当前快照切换必须在事务内锁定并校验任务 token、未过期租约和可提交状态，校验与提交之间不允许另一个 worker 完成接管。旧 worker 恢复后只能保留失败/`ABANDONED` 证据，不能提交正式结果。行锁领取与唯一任务键本身不能替代此校验。

持久化、选择与发布的边界固定如下：

1. 下载/读取前先保存 run 起始记录。正式事务前持久化可读原始证据、不可变输入清单与事实候选；失败候选不可被正式查询选中，按无引用对象保留策略清理。原始证据须先通过可读性与完整性校验。
2. 在数据库提交单元内校验租约、候选输入、目标 coverage 尚未终结及适用的预期父快照，然后写入事实版本的有效引用、run/任务结果、缺口和 coverage 计数/终态。同一任务及输入已提交时返回已有结果；相同版本已存在但输入 hash 不同必须报冲突，不能覆盖。任务结果、run 及 revision 不得出现提交一部分的情况。
3. 普通单日发布在同一提交单元内创建系列快照、以比较并交换方式更新作用域唯一的当前快照指针、记录替代关系，并写入具有唯一 `event_id` 的待发布记录（transactional outbox 或同等持久机制）。竞争者若已改变父快照，本次不得覆盖其指针，须基于新父快照重新校验候选系列。
4. 多日历史修订可先分别提交各日候选 coverage，保持旧当前快照不变；全部受影响范围封存后，由持有有效租约的最终发布任务在一个数据库事务内完成范围完整性校验、新系列快照登记、当前指针切换及 outbox 写入。尚未被已发布快照引用的 `SEALED` 候选不属于默认查询输入。
5. 数据库提交后只执行外部事件投递，不再依赖进程内存补写权威当前指针。投递器扫描持久待发布记录并失败重放；交付语义为至少一次，消费者在其业务提交边界按 `event_id` 去重。事件携带作用域、父/新快照 ID 和发布序号，乱序或重复事件不得回退下游当前版本。
6. 必须验证“证据已保存但数据库回滚”“数据库已提交但尚未投递”“已投递但确认丢失”均可恢复。失败 run 在独立审计提交中记录错误；进程崩溃留下的未完成 run 在恢复时标记 `ABANDONED`。不得出现已发布快照引用未提交事实、不可读证据或半段修订历史的状态。

### 5.3 停机补偿

1. 固定当前 source policy 与系列快照，从其中连续 `SEALED` 水位（而非最大日期或尚未发布的候选 coverage）和 `bootstrap_start_date` 计算缺口范围。首次无水位时，起点、最早回放日期和股票池快照必须是显式登记值；不兼容契约的水位分别计算。
2. 用 PIT 交易日历生成未封存的实际交易日；按日期由旧到新建独立、幂等任务。周末/节假日不应制造假缺口。
3. 根据记录区分 QMT 本地是否下载过、范围是否覆盖、下载调用是否失败、上游是否失败，再写相应 gap 分类；不能用空 DataFrame 一次判断全部原因。证据不足时保留 `UNKNOWN_MISSING`，补充诊断后再分类。
4. 日终封存、缺口重试和供应商修订各产生可追踪 run；重试耗尽时 coverage 为 `DEGRADED`，不是 `SEALED`。
5. 补偿限流不得抢占实时交易和当日封存所需的 QMT 连接/订阅配额。
6. 独立检查除权/供应商修订及未完成发布记录；连续封存水位只回答缺口问题，不能跳过第 4.4 节已封存历史的修订检查，也不能替代 outbox 重放。

## 6. 趋势、榜单与 PIT 依赖

### 6.1 趋势计算

趋势策略覆盖分钟、日、周、月。任何 MA/EMA 等指标必须引用已登记的 `(series policy, canonical_base_interval, derived interval, bar_count, derivation_contract_version)`，每次计算再固定 `series_snapshot_id` 和实际输入清单；例如 `MA20@1d`、`MA20@5m`、`MA20@1w` 不是同一指标。`SUSPENDED`/`NO_TRADE` 不伪造有效 bar，预热不足须返回明确状态；跨契约或复权快照的连续计算遵守第 4.3、4.4 节。策略不得因图表请求或临时缓存而获得未覆盖的基础序列。

### 6.2 四类检测与榜单场景的边界

| 场景 | 数据状态 | 结果规则 |
| --- | --- | --- |
| 日终全市场异动检测 | 当前日 `SEALED` 日线 coverage | 只处理正式日线；缺口/降级直接阻断或显示不完整。 |
| 日终正式涨幅榜 | 当前日 `SEALED`，且所有 PIT 依赖可读 | 持久/可复算结果，必须保存完整输入清单。 |
| 板块内个股趋势和领涨股 | 目标日/周期的可用 coverage + PIT 板块成员 | 依赖当时板块成员与分类，不从当前成员表回推历史。 |
| 盘中预览榜单 | 实时/未完成数据，`is_final=false` | 单独命名为预览；不得与日终正式榜单混称或替代。 |

每一份日终正式榜单必须绑定并可读回：

- `universe_snapshot_id`；
- `sector_membership_snapshot_id`；
- 分类体系、版本和 `as_of_date`；
- `series_snapshot_id`、完整日线 coverage 键（含 `coverage_revision`）、`coverage_manifest_id` 及逐标的复权快照引用；
- `source_selection_policy_id`；
- 涨幅计算口径（如 QMT 前复权 `close` 相对哪个前复权 `pre_close`、或其明确派生口径）；
- 排名时间点；
- 纳入/排除规则及其证据：新股、ST、停牌、退市、无成交、流动性过滤。

同一份榜单的筛选、涨幅计算和排序固定同一输入快照。历史数据修订后，旧榜单保持原快照可复算，最新口径榜单另生成版本；未重算的结果必须标识其输入版本，不能与修订后的最新结果混称。

证券主数据、交易日历、上市/退市状态、股票池快照、板块成员和行业分类历史是外部不可变 PIT 依赖契约，不进入 K 线事实表。尤其不得假设 QMT 当前 `get_stock_list_in_sector` 的结果等价于历史某日的板块成员；历史榜单必须引用该日可读取的成员快照。

## 7. 实时交易行情安全契约

实时流仅服务已批准的小交易标的集合。每个订阅必须记录订阅范围/订阅号、来源与契约、订阅健康状态、来源最后行情时间、应用接收时间、心跳结果、断线/重连次数、最大可接受陈旧度和当前未知时间窗口。

1. 无心跳、回调停止、接收时间超过陈旧度、来源时间倒退/不可解析、或断线期间无法确定是否遗漏行情时，创建未知窗口并将关键标的置为 `STALE_DATA`。
2. `STALE_DATA` 下禁止新开仓；已有订单处置和风控动作仍须记录，但不得把“没有新 Tick”当成“行情稳定”。
3. 恢复条件是重连成功、订阅健康恢复、未知窗口以历史补洞或明确不可补的状态处理、窗口数据与当前契约验证通过；仅收到一条新行情不足以解除。
4. 交易、撤单、风控拒绝和最终回报必须写 `trade_market_snapshot`。快照保存真实可读取的 Tick/分钟窗口（或受保留策略保护的不可变对象引用）、来源契约、订阅健康/陈旧状态、策略和参数版本、信号、风控决定、订单请求和最终回报。hash 可附带校验，但不能取代可读取行情证据。

## 9. 已固定与待业务确认的边界

本文已固定：QMT 为默认长期主来源、长期基础 K 线为 QMT 前复权、固定不填充、默认 display-only 不下载、首期全市场日线、分钟/coverage item/交易快照按阶段启用、最近 3 个完整月仅是运行缓冲默认值。版本清单、复权修订、租约提交校验和原子发布是数据可信的必要条件，不随可选 `coverage_item` 的启用而开关；明确的机器错误状态不能被默认降级隐藏。

仍必须由业务所有者在启用相应能力前决定并登记：

1. `display_download_policy_id` 的获批产品入口、单请求最大历史范围、QMT 磁盘配额和并发预算；若不批准，始终返回 `HISTORY_NOT_CACHED`。
2. 每个分钟/回测/训练数据集的标的范围、基础周期、最早回放日期、运行缓冲、归档保留和删除前校验。
3. 日终正式榜单的确切涨幅公式、分类体系、PIT 快照来源、ST/新股/停牌/退市/无成交/流动性排除阈值。
4. 实时交易关键标的的最大陈旧度、心跳定义、未知窗口处理以及 `STALE_DATA` 解除审批。
5. `coverage_item` 是否值得启用及其容量、月分区、冷归档和 revision 保留预算。
6. 现有不复权历史是否另行批准从 QMT 以 `front` 全量回读、封存后切换；未批准时隔离旧序列，并按第 4.3 节拒绝跨不兼容版本的连续查询。
7. 所选 API 家族及能力验收结果；各证券品类的时段口径、盘后交易范围、最早封存时点、复核间隔和重试截止时间。未验证前不能生成正式 coverage。
8. 每个数据集的除权/历史修订检查频率、最大未核验时长、回读范围与预算、合法无成交证据源；资源不足时保留旧快照及待修订状态，不能以不回读的方式继续拼接。
